# The disassembler

Everything in `src/` was generated by `tools/disasm.py` from the original
ROM, plus the hand-written hints in `tools/disasm_hints.json`. It is a
static, recursive-descent 65816 disassembler written for this game; it
emits ca65 source and a report (`docs/disasm_report.md`, shown in
[Progress](progress.md)).

The generator is deterministic: run on the original ROM with the committed
hints, it reproduces `src/` and the report exactly. Since milestone 1,
though, **the committed `src/` is the source of truth**. It gets edited by
hand (names, comments, more files), and the generator is only used to find
improvements, which are then carried over to `src/` by hand or by a script.

## Running it

```sh
python3 tools/disasm.py ROM [--hints tools/disasm_hints.json] [--cdl FILE] \
                            [--out src] [--report docs/disasm_report.md]
```

`ROM` must be the 1 MiB original. The defaults write into `src/` and
`docs/disasm_report.md`, **overwriting hand edits**; `make disasm
BASEROM=path/to/contra3.sfc [CDL=path/to/contra3.cdl]` does the same. Only
use those while the generator is still the source of truth.

### Regenerating into a scratch directory

To see what a change to the generator or the hints does, write the output
somewhere else and compare it with the committed source:

```sh
python3 tools/disasm.py path/to/contra3.sfc --out /tmp/c3/src --report /tmp/c3/report.md
diff -r src /tmp/c3/src
diff docs/disasm_report.md /tmp/c3/report.md
```

Pass `--report` too: without it the report still goes to
`docs/disasm_report.md`. The output directory gets the 32 bank files plus
`main.asm`, `common.inc`, `snes_registers.inc` and `contra3.cfg`.
It takes about ten seconds and prints a one-line summary such as

```
code 134190 bytes, data 914386 bytes, 58012 instructions, 8024 labels, 0 conflicts, 0 stops
```

The ROM that `make` builds is identical to the original, so
`build/contra3.sfc` works as the input. With today's hints, regenerating
from it gives no differences at all, which is a quick way to check that the
committed source and the generator are still in sync.

## How it works

The module docstring of `tools/disasm.py` has the details. In short:

1. **Seeds.** The reset, NMI and IRQ vectors (see
   [The cartridge](cartridge.md#vectors)), the hints' entry points, and,
   with a CDL, every instruction start the emulator saw executed.
2. **Recursive descent.** A worklist follows each path with a CPU state:
   the M and X widths, the data bank (DB) when known, a model of what was
   pushed since the routine's entry, and the last immediate loaded into A.
   - `REP`/`SEP` change M/X; `PLP` restores the widths saved by the matching
     `PHP`.
   - DB is tracked through `PHK`/`PLB`, `LDA #n`/`PHA`/`PLB`, `PEA`/`PLB`
     and `MVN`.
   - After a `JSR`/`JSL`, decoding goes on assuming the callee preserved
     M/X/DB, unless a hint or the return-state inference says otherwise.
   - The same instruction may be reached with different widths as long as
     its length doesn't change; otherwise it is a conflict and is reported.
   - `BRK`, `COP`, `WDM` and `STP` are taken as "this is not code" and stop
     decoding, unless a hint forces them.
3. **Jump tables.** `JMP (abs,X)` and `JSR (abs,X)` read a table of words in
   the program bank, and the patterns `lda table,x / sta ptr / jmp (ptr)` and
   the long form ending in `jml [ptr]` (3-byte entries) are recognised too.
   The length of a table is guessed (stop at the first implausible pointer,
   at existing code or a label, or at a known entry point) unless a hint
   gives it, and the analysis is repeated until it is stable.
4. **Return-state inference.** Routines whose every `RTS`/`RTL` leaves M/X
   different from how they were entered are recorded, and the analysis
   reruns so that their callers resume with the right widths.
5. **Unreferenced routines.** Code that follows the end of a known routine
   and decodes into something plausible is decoded too, and marked in the
   source with the comment `(no caller found; decoded because it follows
   the end of a routine)`.
6. **Pointer recovery.** `lda #lo / sta p` plus `lda #bank / sta p+2` pairs,
   ROM pointers passed in X or Y to routines that read through them, and
   tables of 16-bit data pointers become label expressions
   (`#.loword(label)`, `#^label`) and `.addr` tables.
7. **Emission.** Every byte not decoded as an instruction is emitted as
   `.byte` data. Operands that point into ROM become labels when the bank is
   certain; everything else stays a number. Operand sizes are always forced
   (`a:` absolute, `f:` long, direct page for numbers below `$100`), and
   `.a8`/`.a16`/`.i8`/`.i16` are written whenever the width changes, with
   `.smart` off, so the source assembles to the same bytes whatever the
   symbols evaluate to. A label that falls inside an instruction becomes
   `name = host + n`. Every label substitution is checked to evaluate to
   the original number.

Labels are named by kind and address: `sub_` for a called or dispatched
routine, `loc_` for a branch or jump target, `tbl_` for a jump table,
`ptrs_` for a table of data pointers, and `data_` for anything else that is
referenced; for example `sub_00FF48` is at `$00:FF48`.

## Hints

`tools/disasm_hints.json` holds everything the generator was told rather
than worked out. Its `_doc` key describes every field:

| field | meaning |
|---|---|
| `fastrom` | label banks `$80-$9F` instead of `$00-$1F` (off: the game runs in `$00-$1F`) |
| `entry_points` | extra code entry points, with their M/X (and DB) |
| `labels` | names for labels, instead of the generated ones |
| `comments` | comment lines emitted above an address |
| `data` | inclusive ranges that are never code |
| `not_code` | addresses the unreferenced-routine heuristic must not decode |
| `force_code` | decode even if the opcode looks suspicious or a hint says data |
| `mx_overrides` | force M/X (and DB) when decoding reaches an address |
| `call_returns` | the M/X widths a routine returns with |
| `noreturn` | routines whose calls don't return |
| `inline_tables` | routines that pop their return address and dispatch through a table right after the call |
| `jump_tables` | fix the length of a jump table |
| `no_auto_table` | don't treat a table at an address as a jump table |
| `pointer_args` | routines that take a ROM pointer in X or Y |

Addresses are written `BB:AAAA`. Today only `labels` has entries: it names
`reset`, `nmi` and `irq`. Everything else in the source was found by the
analysis alone.

## CDL input

A code/data log (CDL) records, while the game runs in an emulator, which
ROM bytes were executed as opcodes or read as data, and with which M/X and
DB. The emulator tracer in the project's private repository writes
`cdl/contra3.cdl` plus a JSON sidecar `contra3.cdl.json` (format "SNESCDL",
version 1). `tools/cdl.py` reads it and turns it into hints:

- the M/X of every executed opcode, when only one combination was seen,
  overrides the static guess (opcodes seen with both widths are left to the
  static analysis);
- bytes only ever read as data or sent by DMA are never decoded as code;
- jump, call and indirect-jump targets become entry points, and executed
  code the static analysis didn't reach is seeded;
- the pointer addresses read by indirect jumps give jump tables a minimum
  length;
- the DB seen at an instruction, when it was always the same, lets its
  absolute operand become a label.

```sh
python3 tools/disasm.py path/to/contra3.sfc --cdl path/to/contra3.cdl --out /tmp/c3/src --report /tmp/c3/report.md
```

The committed source was generated without a CDL.
