# The disassembler

The code and data in `src/` were generated by `tools/disasm.py` from the original
ROM, with the hand-written hints in `tools/disasm_hints.json` and the code/data
log (CDL) recorded by the emulator tracer of the project's private companion
repository (see [CDL input](#cdl-input)). It is a recursive-descent 65816
disassembler written for this game; it emits ca65 source and a report
(`docs/disasm_report.md`, shown in [Progress](progress.md)).

**The committed `src/` is the source of truth.** It was generated for the
last time with the CDL; from then on it is edited by hand (names, comments,
more files), and the generator is only a reference and research tool: run it
to find improvements, then carry them over to `src/` by hand or by a script.
That is why it writes into `build/disasm/` by default, never into `src/`.

## Running it

```sh
python3 tools/disasm.py ROM [--hints tools/disasm_hints.json] [--cdl FILE] \
                            [--out build/disasm/src] [--report build/disasm/disasm_report.md]
# or
make disasm BASEROM=path/to/contra3.sfc [CDL=path/to/contra3.cdl]
```

`ROM` must be the 1 MiB original. The output directory gets the 32 bank
files plus `main.asm`, `common.inc`, `snes_registers.inc` and
`contra3.cfg`, and the report goes next to it. It takes about fifteen
seconds and prints a one-line summary such as

```
code 134190 bytes, data 914386 bytes, 58012 instructions, 8046 labels, 0 conflicts, 0 stops
```

Then compare with the committed source:

```sh
diff -r src build/disasm/src
diff docs/disasm_report.md build/disasm/disasm_report.md
```

The ROM that `make` builds is identical to the original, so
`build/contra3.sfc` works as the input. With the committed hints and the same
CDL, the output is identical to `src/` as it was committed in the CDL pass;
without a CDL it differs (no CDL comments, a few operands that only the CDL
could resolve stay numbers, a few false pointers come back). As `src/` gets
edited by hand, the differences grow: they are expected. In particular the
generator still writes one file per bank (`bank_00.asm` ...) with RAM
operands as numbers, so it cannot reproduce the current layout (see
[Source layout](layout.md)) or the RAM symbols; compare by content, e.g.
through the label file `build/contra3.lbl` or by assembling both.

## How it works

The module docstring of `tools/disasm.py` has the details. In short:

1. **Seeds.** The reset, NMI and IRQ vectors (see
   [The cartridge](cartridge.md#vectors)) and the hints' entry points.
2. **Recursive descent.** A worklist follows each path with a CPU state:
   the M and X widths, the data bank (DB) when known, a model of what was
   pushed since the routine's entry, and the last immediate loaded into A.
   - `REP`/`SEP` change M/X; `PLP` restores the widths saved by the matching
     `PHP`.
   - DB is tracked through `PHK`/`PLB`, `LDA #n`/`PHA`/`PLB`, `PEA`/`PLB`
     and `MVN`.
   - After a `JSR`/`JSL`, decoding goes on assuming the callee preserved
     M/X/DB, unless a hint or the return-state inference says otherwise.
   - The same instruction may be reached with different widths as long as
     its length doesn't change; otherwise it is a conflict and is reported.
   - `BRK`, `COP`, `WDM` and `STP` are taken as "this is not code" and stop
     decoding, unless a hint forces them.
   - With a CDL, every executed instruction gets the M/X it ran with (when
     it always ran with the same widths) and the DB it ran with, overriding
     the static guesses.
3. **Jump tables.** `JMP (abs,X)` and `JSR (abs,X)` read a table of words in
   the program bank, and the patterns `lda table,x / sta ptr / jmp (ptr)` and
   the long form ending in `jml [ptr]` (3-byte entries) are recognised too.
   The length of a table is guessed (stop at the first implausible pointer,
   at existing code or a label, or at a known entry point) unless a hint
   gives it, and the analysis is repeated until it is stable.
4. **Return-state inference.** Routines whose every `RTS`/`RTL` leaves M/X
   different from how they were entered are recorded, and the analysis
   reruns so that their callers resume with the right widths.
5. **Unreferenced routines.** With a CDL, executed code that the descent
   didn't reach is seeded first (for this game there is none). Then code
   that follows the end of a known routine and decodes into something
   plausible is decoded too, and marked in the source with the comment
   `(no caller found; decoded because it follows the end of a routine)`.
6. **Pointer recovery.** `lda #lo / sta p` plus `lda #bank / sta p+2` pairs
   in straight-line code, ROM pointers passed in X or Y to routines that read
   through them, and tables of 16-bit data pointers become label expressions
   (`#.loword(label)`, `#^label`) and `.addr` tables. With a CDL, a candidate
   whose code ran but whose target was never read is rejected: it was two
   numbers, not a pointer.
7. **Emission.** Every byte not decoded as an instruction is emitted as
   `.byte` data. Operands that point into ROM become labels when the bank is
   certain; a reference into the middle of a table becomes `table+n`;
   everything else stays a number. Operand sizes are always forced (`a:`
   absolute, `f:` long, direct page for numbers below `$100`), and
   `.a8`/`.a16`/`.i8`/`.i16` are written whenever the width changes, with
   `.smart` off, so the source assembles to the same bytes whatever the
   symbols evaluate to. A label that falls inside an instruction becomes
   `name = host + n`. Every label substitution is checked to evaluate to
   the original number. The internal header and the vectors at the end of
   bank `$00` get one annotated line per field (see
   [The cartridge](cartridge.md#the-internal-header)).

Labels are named by kind and address: `sub_` for a called or dispatched
routine, `loc_` for a branch or jump target, `tbl_` for a jump table,
`ptrs_` for a table of data pointers, and `data_` for anything else that is
referenced; for example `vector_length` is at `$00:FF48`.

## Hints

`tools/disasm_hints.json` holds everything the generator was told rather
than worked out. Its `_doc` key describes every field:

| field | meaning |
|---|---|
| `fastrom` | label banks `$80-$9F` instead of `$00-$1F` (off: the game runs in `$00-$1F`) |
| `entry_points` | extra code entry points, with their M/X (and DB) |
| `labels` | names for labels, instead of the generated ones |
| `comments` | comment lines emitted above an address |
| `data` | inclusive ranges that are never code |
| `not_code` | addresses the unreferenced-routine heuristic must not decode |
| `force_code` | decode even if the opcode looks suspicious or a hint says data |
| `mx_overrides` | force M/X (and DB) when decoding reaches an address |
| `call_returns` | the M/X widths a routine returns with |
| `noreturn` | routines whose calls don't return |
| `inline_tables` | routines that pop their return address and dispatch through a table right after the call |
| `jump_tables` | fix the length of a jump table |
| `no_auto_table` | don't treat a table at an address as a jump table |
| `pointer_args` | routines that take a ROM pointer in X or Y |

Addresses are written `BB:AAAA`. Today `labels` names `reset`, `nmi` and
`irq`, and `mx_overrides` plus `comments` give DB `$05` to three routines
that never ran in the CDL traces (`check_button_code_unused`, `check_30_lives_code`, `check_stage_select_code`,
which look like button-code checks) and to `queue_vram_block_at_map_position`, so that their
tables in bank `$05` became labels. Everything else was found by the
analysis and the CDL.

## CDL input

A code/data log (CDL) records, while the game runs in an emulator, which
ROM bytes were executed as opcodes or read as data, and with which CPU
state. The private repository's tracer (a patched snes9x libretro core that
plays scripted and random sessions of every stage, difficulty and mode)
writes `cdl/contra3.cdl` plus a JSON sidecar `contra3.cdl.json`, format
"SNESCDL" version 1. `tools/cdl.py` reads it; its docstring summarises the
format:

- a 64-byte header (`"SNESCDL\0"`, version, header size, ROM size, ROM
  SHA-1, WRAM plane size), then per ROM byte:
- plane A: opcode, operand, read as data, read by DMA, and on opcodes the
  M and X widths it ran with (both widths can be set);
- plane B: emulation/native mode, and whether the byte was the target of a
  call, a jump, an indirect jump, an RTS/RTL dispatch, an interrupt, or was
  read as an indirect-jump pointer;
- a WRAM plane (code run from RAM: none in this game);
- readers: the address of the first instruction that read each byte (for
  DMA, the one that started the transfer);
- the sidecar lists every dynamic jump (source, target, pointer address) and,
  for every executed opcode, the DB and D values it ran with.

What the generator does with it:

- the M/X of every executed opcode overrides the static guess (per flag:
  a flag seen with both values is left to the static analysis);
- the DB seen at an instruction replaces the statically tracked one; when
  only one DB was seen, an absolute operand of `$8000` or more becomes a
  label in that bank (or, with DB `$7E`/`$7F`, is known to be WRAM), and an
  operand that would read as a register name is left a number when the code
  ran with DB `$7E`/`$7F`;
- bytes only ever read as data are never decoded as code;
- pointer candidates are checked against what was really read (see step 6);
- pointer addresses read by indirect jumps give jump tables a minimum
  length;
- the source gets three kinds of comments:
  - `; (not executed in the CDL traces)` where a stretch of code that never
    ran starts;
  - on a direct-page operand of an instruction that ran with D other than 0,
    the address really accessed, e.g. `stz $16 ; $1316 (D=$1300) / $1356
    (D=$1340) / $1F16 (D=$1F00)`;
  - above data, `; CDL: read by sub_X, sub_Y`, `; CDL: DMA (started in
    sub_X)` or `; CDL: not accessed`, naming the routine that contains the
    first instruction that read the bytes.

### What the CDL showed

The report's "Comparison with the CDL" table has the numbers. In short:

- **Code.** Every byte the game executed (119,225) was already decoded by
  the static analysis, with the same instruction boundaries; none of the
  decoded code was read as data. The other 14,965 decoded bytes never ran:
  unexecuted branches, routines nothing in the traces called, and all 73
  routines found by the unreferenced-routine heuristic. They lie in bytes
  the CDL never touched, so they stay code.
- **Jump tables.** All 1,261 dynamic jumps go to entries of tables the
  static analysis had found; no table turned out to be longer. Some entries
  were never used in the traces.
- **M/X.** Only 4 instructions were decoded with other widths than they ran
  with (after calls whose callee returns with other widths depending on
  the path); only the `.a8`/`.a16` directives changed.
- **DB.** Most instructions run with DB `$05`. The CDL gave the bank of the
  83 absolute operands of `$8000+` the static analysis couldn't resolve, and
  corrected the static DB in 19 places (for example the reset code: its
  `MVN` clears the stack area, so the `PLB` that follows pulls `$00`, not the
  `$05` that was pushed). The five that remained, in four routines that
  never ran, were resolved with hints. No absolute operand of `$8000+` is a
  number anymore.
- **D.** The direct page is `$0000` almost everywhere; 207 instructions run
  with D `$1300`, `$1340` or `$1F00` (some with more than one) and are
  annotated.
- **False pointers.** Five immediate pairs were no pointers (for example
  `$AAAA`/`$02`, an OAM fill value, and `$FFF6`/`$00`, which had created a
  label inside the vector table), and one pair joined two unrelated
  routines; they are numbers now.
